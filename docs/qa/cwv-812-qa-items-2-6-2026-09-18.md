## Two findings outside the QA list

### 1. The cloaking is not just faking the score, it is breaking analytics

On production today, `snippets/optimization.liquid` converts scripts to `type="text/lazyload"`
and is supposed to restore them on first interaction. It does not.

Measured on `/collections/treadmills`, real Chrome, after real mouse and scroll input and after
dispatching every event the injector listens for, waiting 12 s:

- 77 scripts still `type="text/lazyload"`
- `loadJSscripts` — **not defined**, so the restore function never exists
- `window.Shopify`, `window.ShopifyAnalytics`, `window.trekkie` — all undefined
- Heatmap, Gorgias: never requested

Same page on the preview: 0 lazyload scripts, `ShopifyAnalytics` and `trekkie` live at 1.6 s.

The restore block is a plain inline `<script>` present in the served HTML, so a hoisted
`function loadJSscripts()` should exist. It does not, which means the block never executed — the
`init` block's MutationObserver rewrites scripts at runtime and takes out the very script that
would have undone it. The restore body also opens with `observer.disconnect()`, and `observer` is
not in scope there, and does `removeChild(t[i])` before `t[i].parentNode.insertBefore(...)`, which
dereferences a null parent. Three independent ways for it to never complete.

Shopify's analytics tag carries `class="analytics"` and line 17 of the snippet is
`e.className == 'analytics' && (e.type = 'text/lazyload')` — it is targeted deliberately.

Caveat worth stating plainly: this was measured from a proxied sandbox. The inline-script and
global-object evidence is not network dependent, but it should be confirmed once from a normal
browser before anyone acts on the analytics angle.

If it holds, Phase 1 is not only an honesty fix. It restores Shopify analytics, Heatmap and
Gorgias chat on the storefront.

### 2. The remanufacturing-process image — located, and it needs no re-upload

Tim assigned locating this to Izza and resizing to Larianne on Sept 14. Located:

- `sections/extra-info.liquid` lines 81 and 97
- `sections/HGS-extra-info.liquid` lines 547 and 559

Both hard-code the full CDN URL as `<img src>` and as the video `poster`:

```
https://cdn.shopify.com/s/files/1/0884/2012/2940/files/Our_Remanufacturing_Process_Video_Thumbnail_-_PDP.png?v=1763416095
```

No `width` parameter, so Shopify serves the original: **132,364 bytes** for an element that
renders at 380 × 214 CSS px on mobile. 116 KB wasted, 88%. Confirms Tim's ~110 KB estimate.

The source file is fine. The URL is the problem. Appending a width parameter, live-tested:

| URL | bytes |
|---|---|
| as-is | 132,364 |
| `&width=1000` | 62,446 |
| `&width=800` | 49,092 |
| `&width=600` | 35,656 |

`&width=800` covers a 2× mobile render and most desktop cases at 49 KB. `&width=600` hits Tim's
"under ~40 KB" target at 36 KB. Either is a four-line theme change on two files — no re-upload,
no new asset, identical visual.
