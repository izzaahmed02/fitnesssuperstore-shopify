## Preview resolution — answers Tim's item 3 fallback question

`?preview_theme_id=` is a 302 plus a `_shopify_essential` cookie. A client that does not carry
that cookie through the redirect silently gets **MAIN**, not the preview — verified: a cookieless
`curl -L` returns theme `186120208700`.

A real headless Chrome (Lighthouse, which is what PSI runs) **does** carry it. Verified: the
Lighthouse run against the preview URL loaded 158 requests including `heatmap`, `gorgias` and
`trekkie`; the same run against production loaded 67 and none of them. So PSI will resolve the
preview param. No fallback needed.

**Self-check for whoever runs PSI:** production is still cloaked, so a cloaked run reports
**TBT 0 ms**. If a PSI run against a preview URL comes back with TBT 0 ms, the preview did not
load and the number is production. Discard and re-run.

#### Two things in the numbers that need reading carefully

**1. Woodway PDP desktop TBT of 3,620 ms.** Far and away the worst figure in the set, and roughly
7.5x the 480 ms measured locally. The PDP is the worst page on every metric on both form factors.
This is not caused by anything in #812 — Phase 1 removes script deferral, it does not add main
thread work — but it is now measured and on the record, and it warrants its own bounded ticket.

**2. Desktop CLS of 0.849 on home and 1.024 on collection.** Both far past the 0.1 threshold, yet
the same pages measure 0.145 and 0.023 on mobile, and the Woodway PDP measures 0.006 on desktop.
That pattern is not a uniform site problem, so it needs explaining rather than recording flat.

The PDP is the clue. Its desktop run has TBT of 3,620 ms, so the main thread is jammed, content
paints late and all at once, and nothing gets a chance to shift. Home and collection paint fast
(FCP 0.8 s) and then late-arriving elements push the page down.

Two elements are confirmed layout-shifters in the local desktop runs:

| Element | Present in production? |
|---|---|
| `#shopify-pc__banner` — Shopify cookie consent banner | Yes, but **only after this PR merges** |
| `#PBarNextFrameWrapper` — Shopify unpublished-theme preview bar, `height: calc(68px + …)` | **No**, preview only |

They score small locally (0.0092 and 0.0018) because the proxied runs were slow enough that both
elements arrived before content painted. On PSI's fast desktop run the order reverses.

So part of this desktop CLS is a preview artifact that will disappear on publication, and part of
it may not be. The consent banner does not currently paint on production at all, because the
cloaking strands the consent script. Phase 1 restores that script. **It is therefore possible that
merging Phase 1 surfaces a desktop CLS problem that the cloaking was accidentally hiding.**

This is a hypothesis, not a finding. It does not block the merge — CLS is not what Phase 1 touches,
and the honest position is that production's current CLS is unmeasurable while the consent script
is broken. Resolving it takes one look at the layout-shift audit on either desktop report to see
which element ranks first. Recommend a bounded follow-up either way: reserve space for the consent
banner so it cannot shift content when it starts painting again.

## Two findings outside the QA list

### 1. The cloaking is not just faking the score, it is breaking analytics

On production today, `snippets/optimization.liquid` converts scripts to `type="text/lazyload"`
and is supposed to restore them on first interaction. It does not.

Measured on `/collections/treadmills`, real Chrome, after real mouse and scroll input and after
dispatching every event the injector listens for, waiting 12 s:

- 77 scripts still `type="text/lazyload"`
- `loadJSscripts` — **not defined**, so the restore function never exists
- `window.Shopify`, `window.ShopifyAnalytics`, `window.trekkie` — all undefined
- Heatmap, Gorgias: never requested

Same page on the preview: 0 lazyload scripts, `ShopifyAnalytics` and `trekkie` live at 1.6 s.

The restore block is a plain inline `<script>` present in the served HTML, so a hoisted
`function loadJSscripts()` should exist. It does not, which means the block never executed — the
`init` block's MutationObserver rewrites scripts at runtime and takes out the very script that
would have undone it. The restore body also opens with `observer.disconnect()`, and `observer` is
not in scope there, and does `removeChild(t[i])` before `t[i].parentNode.insertBefore(...)`, which
dereferences a null parent. Three independent ways for it to never complete.

Shopify's analytics tag carries `class="analytics"` and line 17 of the snippet is
`e.className == 'analytics' && (e.type = 'text/lazyload')` — it is targeted deliberately.

Caveat worth stating plainly: this was measured from a proxied sandbox. The inline-script and
global-object evidence is not network dependent, but it should be confirmed once from a normal
browser before anyone acts on the analytics angle.

If it holds, Phase 1 is not only an honesty fix. It restores Shopify analytics, Heatmap and
Gorgias chat on the storefront.
