# Feed `condition` column — the rule, the source, and the QA target

## The rule

**Every row of every primary feed outputs exactly lowercase `new` or lowercase
`refurbished`.** No blanks, no padding, no other value, no other casing. Per
Tim, Sept 9 2026. Remanufactured products map to `refurbished`.

`refurbished` is Google's and Microsoft's enum value for our remanufactured
machines; it is a destination enum, not customer-facing copy. Our own
terminology in the catalogue, on the storefront and in any customer-facing text
stays **new / remanufactured** — this document changes one feed column and
nothing else.

## The only condition source in the catalogue

```
custom.condition_state   product metafield, single_line_text_field
```

There is no variant-level equivalent and no second source. Specifically
verified against live Shopify, 2026-09-10:

| Candidate | State |
| --- | --- |
| `mm-google-shopping.condition` (variant definition exists) | **0 metafields**, catalogue-wide |
| `mm-google-shopping.condition` (product, unstructured) | **absent**; the only keys present in that namespace are `google_product_category` (4,297) and `age_group` (177) |
| `custom.condition`, `custom.feed_condition`, `custom.google_condition` | no such metafield — all 173 distinct `custom` keys in the catalogue were scanned; `condition_state` (4,501) is the only condition-shaped one |
| Product tags | one product in the feed cohort carries a `Remanufactured` tag; nothing else condition-shaped |

So the mapping is one line, and it is the same line the Phase 2 generator
already uses (`scripts/phase2_feed_generator.py`):

```
condition = "refurbished" if condition_state == "Remanufactured" else "new"
```

## The Shopify source is clean — the defect is in the app

Tim's Sept 9 audit of the feed output: 45 rows `New`, 6 rows `Refurbished`, 12
blank, 8 with trailing spaces, and 1 row with condition `149`. 72 rows.

**None of that is in Shopify.** A full bulk export of all 6,483 products, then
the 2,450-product feed cohort isolated by collection membership, gives exactly
two values and nothing else:

| `custom.condition_state` in the feed cohort | Products | Variant rows |
| --- | --- | --- |
| `Remanufactured` | 1,241 | 1,241 |
| `New` | 1,209 | 1,264 |
| blank | **0** | 0 |
| leading/trailing whitespace | **0** | 0 |
| any other value | **0** | 0 |

Two independent scans confirm it: the metafield scan above, and a scan of every
`custom` metafield and every tag on all 2,450 cohort products for a
condition-shaped value. `condition_state` is the only field that holds one, and
it holds only those two.

**Consequence for the fix.** The 72 bad rows are produced inside the Multifeeds
`condition` field configuration, not by product data. So this is one expression
per feed in the app admin — not 72 product edits — and nothing in Shopify or in
this theme needs to change to fix it. That also means it cannot be fixed or
verified from this repo: the app admin is the only place the change can be made.

Feeds are generated by **Multifeeds** (`multiple-google-shopping-feed`, by
WoolyTech); the field mapping lives in the app's admin and is not in this repo.
Same as the offer-ID work — see `docs/google-feed-offer-id.md`.

## The change, per feed

Multifeeds > Settings > the feed > Edit primary feed. The field-mapping tabs are
Meta, Target, Basic, Media, Identifiers, Detail, Label, Shipping, AI, Others,
Custom.

**`condition` is not on the Basic tab.** Basic carries only Item
identification, Product data and Availability — confirmed from that screen on
`googleshoppingfs`. Google groups `condition` with the detailed product
attributes, so **Detail** is where to look first; Identifiers holds
brand/GTIN/MPN, and Others / Custom are the fallbacks.

Set the field to a total expression over the one source, with no fall-through
that can emit anything else:

```
if   lower( trim( Product metafield (condition_state) ) ) == "remanufactured"
then "refurbished"
else "new"
```

Three properties make this stay fixed, which is what Tim asked for:

- **`trim` before the compare**, so a value that later picks up padding still
  classifies, instead of falling to the else branch by accident.
- **Both branches are literals.** No branch reads a metafield through to the
  output, so no product value can ever reach the column. A blank, a stray
  `149`, or a new casing cannot appear again regardless of what happens in the
  catalogue.
- **No third branch and no default.** A product with no `condition_state` emits
  `new` rather than a blank. That is deliberate — see the caveat below — and it
  means the column can never be empty.

Both live primary Google feeds and the live Bing feed need it:

| Feed | Multifeeds group | Live rows |
| --- | --- | --- |
| `googleshoppingfs` | New Feeds Other - Larianne test | 1,537 |
| `googleshoppingfrenchfitness` | New Feeds FF - Larianne test | 968 |
| `bingshoppingnew` | Bing main feed - Larianne test | 2,505 |

The Bing feed carries all three feed collections, so its cohort is the union of
the two Google ones.

**The group name, not the feed name, identifies a feed.** Names repeat across
groups: a `googleshoppingfs` and a `googleshoppingfrenchfitness` also sit in the
plain `New Feeds` group, both Paused and Disconnected, and editing those changes
nothing. Worse, the Aug 12 feed inventory records a *second* `bingshoppingnew`,
in the `Bing main feed` group, as **Enabled with confirmed active sync** on a
different cohort (2,418 products). If it is still serving it needs the same
expression, and the 2,505-row count below does not apply to it. Confirm its
state before treating the Bing side as done.

**Preview before saving.** The Edit primary feed screen carries Preview and Run
history. Preview must show only `new` and `refurbished` before the change is
saved. Worth stating because the Aug 12 pilot recorded Preview as unusable on
the French Fitness feed after 14+ attempts, so a Preview that does not open is a
known failure of that feed's UI rather than a fault in the expression — fall
back to checking the regenerated file with `scripts/feed_condition_check.py`.

## QA target — the expected output

Derived from live Shopify, 2026-09-10. These are the row counts the corrected
feeds must show, and the numbers Tim asked Iqra to send:

| Feed | `new` | `refurbished` | any other value | Total rows |
| --- | --- | --- | --- | --- |
| `googleshoppingfs` | 296 | 1,241 | **0** | 1,537 |
| `googleshoppingfrenchfitness` | **968** | **0** | **0** | 968 |
| `bingshoppingnew` (Larianne test) | 1,264 | 1,241 | **0** | 2,505 |

`googleshoppingfrenchfitness` is 100% `new` — every product in
`French Fitness - Meta Feeds` carries `condition_state = New`. **Any
`refurbished` row in that feed is wrong**, which locates Tim's 6 `Refurbished`
rows: their correct value is `refurbished`, so those products are
Remanufactured, so they are in `googleshoppingfs`. The 45 `New` rows could be in
either feed. The three feed collections do not overlap
(verified: 0 products shared between any pair), so the per-feed counts add up
exactly.

Row counts drift as products are added — the FF cohort was 966 rows on Sept 9
and is 968 today. Refresh the expectation file rather than reusing these
figures if the totals no longer match.

## Two allowed values is not the same as correct

A feed that emitted `new` on all 1,537 rows would satisfy "the column contains
only new and refurbished, zero other values". It would also declare 1,241
remanufactured machines as new to both Google and Microsoft.

So QA is per row, not per column. `scripts/feed_condition_check.py` does both:

```sh
python3 scripts/feed_condition_check.py googleshoppingfs.tsv \
    --expected docs/google-feed-condition-expected.csv \
    --feed googleshoppingfs
```

It prints the row counts of each value, classifies every offending row in Tim's
own categories (wrong case, blank, padded, unmapped), and joins each row to its
expected value. Without `--expected` it is a shape check only and says so.

The join key is `(item_group_id, old_id)`, the same pair
`scripts/feed_offer_id_diff.py` uses: `old_id` alone is not unique, because five
hex-dumbbell SKUs also exist as standalone Set products in
`googleshoppingfrenchfitness`.

`--feed` is required, because the expectation file covers every feed and
checking one export against all of them reports the other feed's rows as
missing. The script refuses rather than guessing.

## `docs/google-feed-condition-expected.csv`

2,505 rows, one per feed variant row: `product_id`, `sku`, `condition_state`,
`expected_condition`, `feed`. Keys are unique and no row is unmapped.

Regenerate whenever the feed cohort changes, from a Shopify bulk export:

```graphql
{ products { edges { node {
    legacyResourceId status
    conditionState: metafield(namespace: "custom", key: "condition_state") { value }
    collections { edges { node { handle } } }
    variants { edges { node { sku } } } } } } }
```

Keep products whose status is `ACTIVE` or `UNLISTED` and whose collections
include `french-fitness-meta-feeds`, `remanufactured-meta-feeds` or
`other-brand-meta-feeds`; emit one row per variant; `feed` is
`googleshoppingfrenchfitness` for the French Fitness collection and
`googleshoppingfs` otherwise.

`UNLISTED` is included because Multifeeds carries unlisted products even with
"Include unpublished products" off — see `docs/google-feed-offer-id.md`. There
are none in the cohort today; the Sept 10 `REMOVE FROM FEEDS` tag closed the one
that was there.

## The `149` row

`149` is not a condition value anywhere in Shopify. Across all 2,450 cohort
products, every tag and every `custom` metafield, exactly three values are
literally `149`, and all three are dimensions:

| Product | SKU | Field | Feed |
| --- | --- | --- | --- |
| `9879190503740` Technogym Plurima Multistation Wall (Remanufactured) | `MF30` | `custom.length_in` | `googleshoppingfs` |
| `9878580789564` French Fitness FFS Silver 8 Stack Multi Jungle Gym (New) | `FFS-8SMJG` | `custom.width_in` | `googleshoppingfrenchfitness` |
| `9879173464380` French Fitness FFB Black 8 Stack Multi Jungle Gym (New) | `FFB-8SMJG` | `custom.width_in` | `googleshoppingfrenchfitness` |

Tim counted **one** `149` row. A fall-through reading `custom.width_in` would
produce two, one for each Jungle Gym; `custom.length_in` produces exactly one,
`MF30`. So `MF30` / `custom.length_in` is the row and field that fits the count.

**That is a lead, not a conclusion** — it is consistent with a mis-mapped
fall-through branch reading a dimension metafield, but the only proof is reading
the feed's current `condition` expression in the app. Whoever opens it should
read and record the existing expression before replacing it; the offer-ID work
turned up a hardcoded branch that looked like a stray patch and was
load-bearing.

The correction is the same either way: with both branches emitting literals, the
row emits `refurbished` (its `condition_state` is `Remanufactured`) and no
product field can reach the column again.

## Caveat — `As is` and `Used` are outside the two-value rule

`condition_state` carries four values catalogue-wide, not two:

| Value | Products | In a feed collection |
| --- | --- | --- |
| `New` | 3,164 | 1,209 |
| `Remanufactured` | 1,331 | 1,241 |
| `As is` | 4 | **0** |
| `Used` | 2 (both DRAFT) | **0** |

None of the six reaches a feed today, so the two-value rule is correct for the
live cohort and there is nothing to fix now. But the rule is not safe by
construction: `As is` and `Used` both fall to the `else` branch and would be
advertised as `new`, which is a condition misrepresentation on a used machine,
not a formatting defect.

The four `As is` products are ACTIVE or UNLISTED and are excluded only by the
feed collections' price, weight and vendor rules — nothing tests condition. A
price or weight edit could pull one in silently.

Two ways to close it, both needing Tim's GO because both change what the column
can emit:

1. **Map them.** Add a branch for `as is` / `used` emitting `used`, Google's and
   Microsoft's third enum value. Accurate, and keeps the column total.
2. **Exclude them.** Tag the six `REMOVE FROM FEEDS`, reusing the existing
   escape hatch that is already rule 8 of all three feed collections.

Recommend (2) now and (1) whenever As-is inventory is meant to be advertised:
excluding is one tag per product and needs no expression change, and As-is units
are one-off stock that the feed cannot keep accurate anyway.
