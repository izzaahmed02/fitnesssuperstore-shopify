# Feed `condition` column — the rule, the source, and the QA target

## The rule

**Every row of every primary feed outputs exactly lowercase `new` or lowercase
`refurbished`.** No blanks, no padding, no other value, no other casing. Per
Tim, Sept 9 2026. Remanufactured products map to `refurbished`.

`refurbished` is Google's and Microsoft's enum value for our remanufactured
machines; it is a destination enum, not customer-facing copy. Our own
terminology in the catalogue, on the storefront and in any customer-facing text
stays **new / remanufactured** — this document changes one feed column and
nothing else.

## The only condition source in the catalogue

```
custom.condition_state   product metafield, single_line_text_field
```

There is no variant-level equivalent and no second source. Specifically
verified against live Shopify, 2026-09-10:

| Candidate | State |
| --- | --- |
| `mm-google-shopping.condition` (variant definition exists) | **0 metafields**, catalogue-wide |
| `mm-google-shopping.condition` (product, unstructured) | **absent**; the only keys present in that namespace are `google_product_category` (4,297) and `age_group` (177) |
| `custom.condition`, `custom.feed_condition`, `custom.google_condition` | no such metafield — all 173 distinct `custom` keys in the catalogue were scanned; `condition_state` (4,501) is the only condition-shaped one |
| Product tags | one product in the feed cohort carries a `Remanufactured` tag; nothing else condition-shaped |

So the mapping is one line, and it is the same line the Phase 2 generator
already uses (`scripts/phase2_feed_generator.py`):

```
condition = "refurbished" if condition_state == "Remanufactured" else "new"
```

## The Shopify source is clean — the defect is not in the catalogue

Tim's Sept 9 audit of the feed output: 45 rows `New`, 6 rows `Refurbished`, 12
blank, 8 with trailing spaces, and 1 row with condition `149`. 72 rows.

**None of that is in Shopify.** A full bulk export of all 6,483 products, then
the 2,450-product feed cohort isolated by collection membership, gives exactly
two values and nothing else:

| `custom.condition_state` in the feed cohort | Products | Variant rows |
| --- | --- | --- |
| `Remanufactured` | 1,241 | 1,241 |
| `New` | 1,209 | 1,264 |
| blank | **0** | 0 |
| leading/trailing whitespace | **0** | 0 |
| any other value | **0** | 0 |

Two independent scans confirm it: the metafield scan above, and a scan of every
`custom` metafield and every tag on all 2,450 cohort products for a
condition-shaped value. `condition_state` is the only field that holds one, and
it holds only those two.

**Consequence.** Wherever those 72 rows are, they are not produced by product
data: the catalogue cannot emit a blank, a padded value or a `149`. So this is a
feed-configuration problem, and nothing in Shopify or in this theme needs to
change. It also cannot be fixed from this repo — the app admin is the only place
a feed expression can be edited.

Which feed carries them is a separate question, and the answer is **not the two
live Google primaries** — see the verification below.

Feeds are generated by **Multifeeds** (`multiple-google-shopping-feed`, by
WoolyTech); the field mapping lives in the app's admin and is not in this repo.
Same as the offer-ID work — see `docs/google-feed-offer-id.md`.

## The condition field — where it is, and what it does today

Multifeeds > Settings > the feed > Edit primary feed. The field-mapping tabs are
Meta, Target, Basic, Media, Identifiers, Detail, Label, Shipping, AI, Others,
Custom.

The field is **Detail > Condition and packing > Condition**. Not Basic — Basic
carries only Item identification, Product data and Availability.

### The live expression, read 2026-09-11

On `googleshoppingfs`:

```
if Product metafield (condition_state) == "New" then New
else if Product metafield (condition_state) == "Remanufactured" then Refurbished
else New
```

`New` and `Refurbished` are unquoted value tokens rather than quoted literals,
and the accessor is the translated `Product metafield (...)` rather than the
`Untranslated ...` form every Custom-tab expression on the same feed uses.

**Both of those looked like defects and neither is.** The live output (below)
settles it: the tokens serialise to Google's lowercase enum values, and the
translated accessor is returning the catalogue value on every row. Recorded
because the appearance is misleading and the reading is worth not repeating.

One real weakness remains. The comparisons are exact and un-trimmed, and
**`else New` is a silent catch-all**: a padded value, an empty one, `As is` or
`Used` all emit `new`. Nothing triggers it in the current cohort, so it is a
latent fault rather than a live one — see the As-is caveat below.

### Root cause — a second condition field nobody was looking at

The Bing feed's Condition is **not** the Google expression. Read from
`bingshoppingnew` > Detail > Condition and packing > Condition:

```
Untranslated Product metaobject reference (product_condition)
```

A raw passthrough, with no mapping and no fallback. It reads `product_condition`
on the **`3rd_party` metaobject** — a per-product vendor-data record attached via
`custom.3rd_party`, 4,654 of them, the same record the shipping expression reads
`estimated_shipping_*` and `google_custom_label_*` from.

So the two feed families read different fields:

| | Source | Mapped? |
| --- | --- | --- |
| `googleshoppingfs`, `googleshoppingfrenchfitness` | `custom.condition_state` | yes, via an if/else |
| `bingshoppingnew` (both) | `3rd_party.product_condition` | **no — raw passthrough** |

That is the whole defect. Whatever text sits in that field lands in the column
verbatim, which is why the values are `New`, `Refurbished`, `new `, blank and
`149` — hand-entered data, never normalised, never validated.

`condition_state` being clean was true and irrelevant: it was never the field
Bing read.

### The `149`, explained

`SPORTSART-G260`'s `3rd_party` record carries `product_condition = "149"` and
`estimated_shipping_overnight = "0"`. The custom shipping expression substitutes
`149` for California whenever overnight is under 1. A California shipping rate
was typed into the condition field of the same record. One keystroke in one
metaobject, surfacing as an invalid condition on two feeds.

### Changing it is feed-only

The theme reads exactly one field from this metaobject, `google_material`, and
uses it solely to show the "On Display in Store" badge. The storefront's own
Condition line reads `custom.condition_state`. So correcting
`product_condition` cannot change anything a customer sees.

## The replacement — hardening, not a repair

```
if   lower( trim( Untranslated Product metafield (condition_state) ) ) == "remanufactured"
then "refurbished"
else "new"
```

**This is hardening, not a repair.** The two live Google feeds already emit the
right value on every row, so nothing here fixes a defect they have. What it
changes is what happens when something unexpected arrives: `lower(trim(...))`
classifies a padded or re-cased value instead of dropping it to the fallback,
and `Untranslated` removes the dependency on a translation row existing. Both
are currently benign, and both are the kind of thing that stops being benign
without warning.

It does **not** close the `else` problem. `As is` and `Used` still land on
`"new"`, because the rule Tim set has only two values — see the caveat below,
which is the one open question that needs his decision rather than a code change.

Apply it only to a feed that actually shows a defect, or as a deliberate
hardening pass across all of them. Changing a clean feed's expression for no
observed fault is a risk with no payoff, and Version history is the record of
what moved.

Both live primary Google feeds and the live Bing feed need it:

## Two allowed values is not the same as correct

A feed that emitted `new` on all 1,537 rows would satisfy "the column contains
only new and refurbished, zero other values". It would also declare 1,241
remanufactured machines as new to both Google and Microsoft.

So QA is per row, not per column. `scripts/feed_condition_check.py` does both:

```sh
python3 scripts/feed_condition_check.py googleshoppingfs.tsv \
    --expected docs/google-feed-condition-expected.csv \
    --feed googleshoppingfs
```

It prints the row counts of each value, classifies every offending row in Tim's
own categories (wrong case, blank, padded, unmapped), and joins each row to its
expected value. Without `--expected` it is a shape check only and says so.

The join key is `(item_group_id, old_id)`, the same pair
`scripts/feed_offer_id_diff.py` uses: `old_id` alone is not unique, because five
hex-dumbbell SKUs also exist as standalone Set products in
`googleshoppingfrenchfitness`.

`--feed` is required, because the expectation file covers every feed and
checking one export against all of them reports the other feed's rows as
missing. The script refuses rather than guessing.

## The `149` row — resolved

It is `SPORTSART-G260`, named above. Two earlier hypotheses are superseded and
are recorded so neither is re-derived:

1. **`custom.length_in` on MF30.** Proposed because it was the only field in the
   Google cohort holding a literal `149` and a fall-through reading it would
   produce exactly one row. Wrong: the condition mapping reads no dimension
   metafield, and MF30 is not the affected row.
2. **A fragment of the custom `shipping` expression.** That expression does
   carry the literal `"149"` twice, as the California overnight fallback:

   ```
   ",US:CA::" + (if abs(default( Product metaobject reference (estimated_shipping_overnight), "0")) < 1
    then "149" else default( Product metaobject reference (estimated_shipping_overnight), "149")) + " USD"
   ```

   A better guess, and still not the answer — that expression is on
   `googleshoppingfs`, whose condition column is clean, and the affected row is
   in the Bing feeds.

`149` is a shipping rate in this catalogue's vocabulary, so a `149` sitting in a
condition field remains most consistent with a stray paste into one product's
override. The override record is what proves it.

## `condition_state` also drives shipping — do not "clean up" the metafield

The Custom tab's `shipping` expression branches on
`Untranslated Product metafield (condition_state) == "New"` before selecting a
rate table. The metafield therefore feeds both the condition column and the
shipping column.

That is a second reason the fix belongs in the feed expression and not in the
catalogue: normalising `condition_state` to lowercase — the obvious-looking way
to make the condition column lowercase — would silently fail that `== "New"`
comparison and move every affected row onto the wrong shipping branch. The
catalogue values stay exactly as they are.

## Caveat — `As is` and `Used` are outside the two-value rule

`condition_state` carries four values catalogue-wide, not two:

| Value | Products | In a feed collection |
| --- | --- | --- |
| `New` | 3,164 | 1,209 |
| `Remanufactured` | 1,331 | 1,241 |
| `As is` | 4 | **0** |
| `Used` | 2 (both DRAFT) | **0** |

None of the six reaches a feed today, so the two-value rule is correct for the
live cohort and there is nothing to fix now. But the rule is not safe by
construction: `As is` and `Used` both fall to the `else` branch and would be
advertised as `new`, which is a condition misrepresentation on a used machine,
not a formatting defect.

The four `As is` products are ACTIVE or UNLISTED and are excluded only by the
feed collections' price, weight and vendor rules — nothing tests condition. A
price or weight edit could pull one in silently.

Two ways to close it, both needing Tim's GO because both change what the column
can emit:

1. **Map them.** Add a branch for `as is` / `used` emitting `used`, Google's and
   Microsoft's third enum value. Accurate, and keeps the column total.
2. **Exclude them.** Tag the six `REMOVE FROM FEEDS`, reusing the existing
   escape hatch that is already rule 8 of all three feed collections.

Recommend (2) now and (1) whenever As-is inventory is meant to be advertised:
excluding is one tag per product and needs no expression change, and As-is units
are one-off stock that the feed cannot keep accurate anyway.

So: create the FF-MSS record with `product_condition = new` to clear the

### 4. The 3 no-product-match rows — they do have a product

`53039894462780`, `53039894495548`, `53039894528316` are **variant IDs**, not

**All three have `sku: null`.** The Bing feed keys on SKU, so a null SKU falls

Three defects on one product, all from the same omission:

Fixing it at source, as Tim asked, is a product-listing job and not a feed edit:
assign the three SKUs, set real weights, then create the `3rd_party` record with
`product_condition = new` (`condition_state` is `New`). The rows leave the feed
only if the product is excluded; otherwise they stay and become correct.

The product sits in no Meta Feeds collection, so it reaches only the
`Bing main feed` group and neither Google feed.

### The mapping expression, with Tim's two corrections

```
if   lower(trim(Untranslated Product metaobject reference (product_condition))) == "used"
then "used"
else if lower(trim(Untranslated Product metaobject reference (product_condition))) == "remanufactured"
  or lower(trim(Untranslated Product metaobject reference (product_condition))) == "refurbished"
then "refurbished"
else "new"
```

Both of Tim's corrections are in: `refurbished` is accepted as well as
`remanufactured`, so a record already carrying the destination value is not
declared new; and `used` has its own branch ahead of the fallback, so the Maxicam
ruling is not overridden by the mapping meant to protect it.

Ships **after** Iqra's data-stage QA passes, never in the same regeneration —
Tim's rule, so a bad count is attributable to one change.
