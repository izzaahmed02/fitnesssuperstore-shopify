# Local Inventory Ads feed — build spec

Per Tim's Sept 5 direction, this feed is a **stable Shopify URL that Merchant
Center fetches on a schedule**, replacing his temporary manual upload
`fs_showroom_local_inventory.tsv`.

## URL

```
https://www.fitnesssuperstore.com/collections/french-fitness-showroom-products?view=local-inventory-tsv
```

The URL never changes. Availability and quantity re-derive from live Shopify on
every fetch, so adding a showroom product or changing its processing time
changes the feed on the next fetch with no code change.

## How membership is handled

The one thing Liquid cannot derive is which offers the primary feed carries.
154 of the 420 variants in the showroom collection have no primary offer, and
nothing readable in Shopify separates them: same product type (`Product Index`),
overlapping tags, all ACTIVE and published, overlapping prices - a $24 vinyl
dumbbell is in the feed while a $22 collar is not.

So membership comes from `snippets/local-inventory-offer-allowlist.liquid`, a
generated list of the 266 offer IDs the primary feeds carry. This splits the
problem the right way round:

- **Changes daily** - availability and quantity, derived live from Shopify.
- **Changes rarely** - which offers exist, regenerated only when the MultiFeeds
  inclusion list changes, which is a controlled change Tim owns.

Regeneration steps are in the header of that snippet.

## Output

Tab-delimited, exactly four columns, header row first:

```
id	store_code	availability	quantity
```

## 1. `id` — the primary feed's legacy gate first, then three schemes

Verified against the live `googleshoppingfs` and `googleshoppingfrenchfitness`
exports. A row whose id does not match the primary offer ID processes as
"Offer does not exist".

Evaluated top to bottom; the first match wins.

| # | Case | Offer ID | Rows in cohort |
| --- | --- | --- | --- |
| 0 | Product `custom.gmc_id_rollout_status` is exactly `approved` **and** product `custom.legacy_gmc_id` is not blank | `custom.legacy_gmc_id` | not recounted, see below |
| 1 | Multi-variant product | `<product ID>-<variant ID>` | 45 |
| 2 | Single-variant with `custom.old_legacy_product_code` | that legacy code (`FFT-CFDI` → `FFA-CFDI`) | 1 |
| 3 | Everything else | `variant.sku` | 220 |

**The primary feed export is the authority on which scheme applies per row —
never assume.** Keying every row on the SKU matches only 225 of the cohort.

### Where step 0 comes from

The primary feeds are generated by Multifeeds (WoolyTech), configured in the
app admin, not in this repo. Both feeds' Item ID expressions open with the same
gate, recorded verbatim in `docs/google-feed-offer-id.md` on branch
`claude/vibrant-gates-93y0z5` (commit `b53ad6c6f`, not on `main`):

```
if   Product metafield (gmc_id_rollout_status) == "approved"
and  Product metafield (legacy_gmc_id) != ''
then Product metafield (legacy_gmc_id)
else ...
```

- `googleshoppingfrenchfitness` expression: lines 305-314 of that doc.
- `googleshoppingfs` expression: lines 76-84.
- Both metafields are `custom` namespace, **product**-level,
  `single_line_text_field`: lines 155-166.

Step 0 copies that gate exactly: product-level, case-sensitive `approved`, and
evaluated before anything else. The value is trimmed of surrounding whitespace
before use. Steps 1-3 are unchanged, so a product that is not `approved`, or is
`approved` with a blank `legacy_gmc_id`, gets exactly the same id as before.
This was checked offline by rendering the old and new snippet with synthetic
data (200 randomised cohorts, byte-identical output).

Step 0 can change the id for a product that is **already** `approved` with a
`legacy_gmc_id` that differs from what steps 1-3 give it. That is intended,
because the primary feed already keys such a product on its `legacy_gmc_id`.
The row counts above were computed under the old rule and have not been
recounted against live Shopify. Before release, diff the feed URL on an
unpublished preview theme against the live one. Before the cutover, every row
that changes must be one that is `approved` with a `legacy_gmc_id` that differs
from its SKU.

## Rubber Hex cutover — ship the resolver with it, then regenerate the allowlist

Today the 45 variants of the old Rubber Hex parent `10247596147004` are
multi-variant rows, so the local feed keys them `10247596147004-<variant ID>`
(step 1). The primary French Fitness feed gets the same ids from its hard-coded
branch for that product ID. All 45 are in the allowlist.

After the cutover the old parent is archived. Each weight is then sold as its
own **single-variant** child product. The primary feed keeps the historical
offer by emitting the child's `custom.legacy_gmc_id` once its
`gmc_id_rollout_status` is `approved`. Without step 0 the local feed would fall
through to step 3 and emit the bare SKU (for example `FF-RCHD50`), which is not
a primary offer id. The allowlist drops that row, so the offer silently loses
its local inventory. If the SKU were ever allowlisted, Google would report
"Offer does not exist" instead.

| SKU | Child product (2026-07-26 matrix) | Local id today | Post-cutover, old resolver | Post-cutover, this resolver |
| --- | --- | --- | --- | --- |
| `FF-RCHD50` | `10347757863228` | `10247596147004-52534101213500` | `FF-RCHD50` (dropped) | the child's `legacy_gmc_id` |
| `FF-RCHD2-5` | `10347757666620` | `10247596147004-52534100721980` | `FF-RCHD2-5` (dropped) | the child's `legacy_gmc_id` |
| `FF-RCHD80-100` | `10347758190908` | `10247596147004-52534105506108` | `FF-RCHD80-100` (dropped) | the child's `legacy_gmc_id` |
| `FF-RCHD5-50` | `10347758256444` (already `approved`, `legacy_gmc_id = FF-RCHD5-50`) | `10247596147004-52534108225852` | `FF-RCHD5-50` | `FF-RCHD5-50` (its existing legacy id) |

Sources, all in git:

- The mapping from SKU to old-parent variant ID is in
  `docs/google-feed-predicted-diff.csv` on `claude/vibrant-gates-93y0z5`. It
  has 45 rows for `10247596147004`, and they match the 45 composites in
  `snippets/local-inventory-offer-allowlist.liquid` exactly.
- Child product IDs, `legacy_gmc_id` and rollout status come from
  `docs/rubber-hex-cutover/rubber-hex-parent-variant-matrix.csv` on
  `claude/rubber-hex-parent-url-ey2m7o`, as of 2026-07-26.

In that matrix, 40 of the 45 children have neither metafield set yet. The value
their `legacy_gmc_id` will get at cutover is not recorded in this repo. To keep
the historical offer, it must be the old composite in the "Local id today"
column.

The other 5 children are the dual-keyed sets `FF-RCHD2-5-22-5`,
`FF-RCHD2-5-25`, `FF-RCHD5-50`, `FF-RCHD5-75` and `FF-RCHD5-100`. They are
already `approved`, each with its own SKU as `legacy_gmc_id`, and already have
their own primary offer. Their old composites therefore have no child to take
them over unless someone decides to re-key those products, which would reset
their own offer history. That decision belongs to the cutover owner. The
resolver just follows whatever the metafields say.

### Release rules

1. **The resolver change ships in the same release as the cutover.** It must
   not ship after, because between the two every Rubber Hex child falls back to
   its SKU and drops out of the local feed. It can ship earlier, because it
   changes nothing for a product that is not `approved` with a `legacy_gmc_id`.
2. **Leave the allowlist unchanged until the cutover.** The current list still
   holds the 45 old composites, so a child whose `legacy_gmc_id` is its old
   composite is admitted even before regeneration. This was checked offline:
   45 approved synthetic children, each keyed on one of the real allowlisted
   composites, all emit.
3. **After the cutover, regenerate the allowlist from the post-cutover primary
   offers.** Use the steps in the header of
   `snippets/local-inventory-offer-allowlist.liquid`: export
   `googleshoppingfs` and `googleshoppingfrenchfitness` after the cutover has
   processed, take the de-duplicated `id` column, and intersect it with the
   local cohort. Composites that no longer exist in the primary feed drop out,
   and any new child ids come in.
4. **Each child must be in `french-fitness-showroom-products` to get a local
   row.** The local cohort is that collection. The 2026-07-26 matrix records
   40 of the children as `Product (Hidden)`. Confirm collection membership
   after the cutover, or the resolver never sees them.
5. After regeneration, confirm in Merchant Center that local inventory shows
   no "Offer does not exist" errors for the Rubber Hex offers.

## 2. `store_code`

`FSS1`. Not changed without Tim's explicit GO.

## 3. Eligibility gate — `custom.processing_time_filter` is primary

| Filter value | Eligible |
| --- | --- |
| `Ships in 2 weeks or less` | yes |
| `Ships in 2-5 weeks` | no |
| `Ships in 5 weeks or more` | no |
| `Out of Stock` | no |

When the filter is **missing**, fall back to the three-metafield cascade,
most-specific-first, and parse the **maximum** stated lead time (the 7 in
"3-7"), eligible at 10 business days or less; weeks convert at 5 business days:

1. `custom.processing_time_long_variant` (variant)
2. `custom.processing_time_long` (product)
3. `custom.processing_time` (product)

Missing both the filter and the cascade = **not eligible**.

In the current cohort 219 rows are gated by the filter and 47 by the fallback
(multi-variant products carry the processing time per variant, so the
product-level filter is unset on them). No row lacks a gate entirely.

## 4. `availability`

| Case | Value |
| --- | --- |
| Eligible | `on_display_to_order` |
| Not eligible | `out_of_stock` |

`on_display_to_order` is the accurate claim for showroom display units that ship
to the customer, and matches the Merchant Center "Products on display in store"
setup and the shipping-policy page. Never publish `in_stock`.

## 5. `quantity`

`1` for eligible, `0` for not eligible. `on_display_to_order` does not require a
quantity, so the `1` is belt-and-suspenders only.

**Never publish Shopify's stored numbers** — 9,989 on FFS-PFRD, 449,511 on the
hex dumbbells, negatives on out-of-stock items. They are orderability
placeholders, not shelf counts, and are what failed Google's inventory
verification on the retired files. True shelf counts are a separate physical
count task and do not block launch.

## 6. Exclusions

A variant with **no primary offer gets no local row**. 154 of the 420 variants
in the showroom collection have no offer in either primary feed — mostly
accessories (bands, collars, bumper plates, medicine balls). Nothing readable in
Shopify distinguishes them: all ACTIVE, all published, overlapping prices (a $24
vinyl dumbbell is in the feed, a $22 collar is not). Expanding the MultiFeeds
inclusion list to add accessories is a separate controlled change after launch
stabilises.
